# Геометрия окна и панелей: как сейчас и что предлагаю поменять

Файл для обсуждения. Ниже — как всё работает в коде сейчас (факты), две
проблемы, которые вы описали, их причины и варианты решения с плюсами/минусами.
Кода я по ширине пока не менял.

## 1. Как это устроено сейчас

### Режим чтения
- Окно шириной `W`. Слева — оглавление `toc_w` (по умолчанию `TOC_WIDTH` = 240,
  тянется мышью, минимум `TOC_MIN_WIDTH` = 120), справа — превью (остаток).
- Текстовая колонка превью **центрируется**: `theme.side_margin(width)` считает
  симметричные поля так, чтобы сама колонка не превышала `MEASURE` = 1300 px.
  На широком экране лишняя ширина уходит в равные поля слева/справа
  (например, на 3440 при оглавлении ~200 px с каждой стороны).
  Поля задаются через `QTextBrowser.viewport().setContentsMargins` — дёшево на
  ресайзе (инвариант 2).

### Вход в правку (`DocumentView._enter_edit`)
1. Запоминается текущая ширина превью: `_preview_width = max(browser.width(), MIN_COLUMN)`,
   где `MIN_COLUMN` = 420.
2. Считается желаемая ширина окна:
   `target = _preview_width + _editor_pref + toc_w + SPLIT_HANDLE*(panes-1)`,
   где `_editor_pref` — ширина редактора (по умолчанию `EDITOR_PREF` = 520, или
   последняя, которую вы выставили мышью).
3. `target` ограничивается `screen.availableGeometry().width() * 0.96` — по
   **тому экрану, где стоит окно** (`window.screen()`, не primary).
4. Если текущее окно уже `target`, вызывается
   `window._view_geometry = window.saveGeometry()` и `window.resize(target, height)`.
   `resize` меняет только размер, `x/y` (левый край) не трогает.

### Раскладка панелей (`viewer.layout_panes`)
- Редактор — **абсолютная** ширина (`_editor_pref`), превью — **остаток**.
- При нехватке места панели уступают по приоритету: **TOC → редактор → превью**.
  Редактор снижается через `EDITOR_MIN` = 360 до `EDITOR_HARD` = 220, затем
  превью опускается до `PREVIEW_HARD` = 260.

### Выход из правки (`DocumentView._leave_edit`)
- Вызывается `window.restoreGeometry(window._view_geometry)` — восстанавливается
  **и позиция, и размер**, снятые на шаге 1 входа.

### Персист
- `MainWindow.closeEvent`: если закрыть приложение **в режиме правки**, в
  `QSettings("geometry")` сохраняется `_view_geometry` (доправчаточная геометрия),
  а не текущая раздутая (инвариант 14). Это про «следующий запуск», не про
  живой цикл.

## 2. Проблема A: окно сдвигается при открытии/закрытии редактора

Вы хотите: **левый край окна не двигается никогда**, меняется только правая
граница (ширина).

### Почему сейчас сдвигается (наиболее вероятно)
- `resize` растёт **вправо**. Если при этом правый край вылезает за пределы
  экрана, оконный менеджер Windows может «поджать» окно, чтобы заголовок
  остался доступен, — то есть фактически сдвинуть его влево.
- На выходе `restoreGeometry` возвращает геометрию, снятую **до** этого сдвига,
  поэтому окно «прыгает» обратно. При повторном входе снова растим и снова
  ловим сдвиг — цикл «открыл/закрыл» выглядит как переезд окна.
- Отдельный случай — **развёрнутое (maximized)** окно: `resize` там либо
  игнорируется, либо `restoreGeometry` разворачивает/сворачивает иначе, и
  поведение становится непредсказуемым.

### Что предлагаю
1. **Анкер по левому краю.** Никогда не менять `x/y`. Целевую ширину считать как
   `min(target, screenRight - x)` (не вылезать за экран справа). Если места
   справа мало — ужимается редактор (политика `layout_panes` уже это умеет), а
   окно стоит на месте.
2. **Живой enter/leave — через явный `setGeometry(x, y, w, h)`,** а не через
   `restoreGeometry`. `restoreGeometry` оставить только для персиста между
   запусками. Так мы гарантируем, что `x/y` не меняются.
3. **Развёрнутое окно.** Если `window.isMaximized()` — вообще не менять размер
   окна; редактор вписывается в текущую ширину (превью сжимается по политике).
   На выходе ничего не восстанавливать.
4. По желанию — при входе в правку **не раздувать окно за пределы**
   `toc + MEASURE + editor + handles` (см. вариант B2): тогда окно не «уползает»
   в ультравайд и левый край точно на месте.

## 3. Проблема B: пропорции редактор/превью разные на 27" и 34"

### Почему
- Редактор — фиксированные `EDITOR_PREF` = 520 px, превью — **остаток**.
  - 27" 2560×1440: превью ≈ 2560 − 240(оглавление) − 520 ≈ 1800 → редактор ≈ 22 %.
  - 34" 3440×1440: превью ≈ 3440 − 240 − 520 ≈ 2680 → редактор ≈ 16 %.
- Вдобавок колонка текста в превью центрируется до `MEASURE` = 1300, поэтому на
  34" превью — это «широкая полоса с большими полями», а редактор визуально
  теряется. На 27" ощущение другое. Отсюда «разные удачные пропорции».

### Варианты (обсуждаемо)

**B1. Редактор — доля ширины, а не px.**
`editor = clamp(ratio * avail, EDITOR_MIN, EDITOR_MAX)`, `ratio ≈ 0.30–0.35`.
- Плюс: на любом мониторе одинаковая доля, предсказуемо.
- Минус: превью перестаёт быть строго «остатком до MEASURE»; нужно подобрать
  клампы, чтобы на узком окне превью не страдало.

**B2. Не раздувать окно шире читаемой колонки.**
Ограничить рост окна в правке: `maxWidth = toc + MEASURE + editor + handles`.
- Плюс: на 34" окно в правке не растягивается на весь экран, пропорции
  редактор/превью совпадают с 27"; левый край стабилен.
- Минус: на ультравайде правка занимает не весь экран (остаются поля вокруг).

**B3. Запоминать долю сплиттера (ratio), а не px.**
В `_on_splitter_moved` хранить `editor / (preview + editor)` и применять как
долю; клампы `EDITOR_MIN/EDITOR_HARD` те же.
- Плюс: ваша ручная настройка переносится между мониторами как пропорция.
- Минус: правка `layout_panes` (сейчас editor — вход-ширина, а не доля).

**B4. Учесть DPI/масштаб.**
Если на 27" масштаб Windows 125 %, а на 34" 100 %, то «одинаковые» пиксели —
не одинаковые физически. Тогда нормировать по `logicalDotsPerInch`.
- Плюс: одинаковые физические пропорции.
- Минус: сложнее; возможно, не ваш случай.

### Моя рекомендация
- Сделать **B3 (доля с клампами)** как основу и **B2** как поведение по
  умолчанию (окно в правке не раздувается шире читаемой колонки). Тогда
  «удачная» раскладка одинакова на 27" и 34", а левый край неподвижен (проблема A).
- B1 — как альтернатива B3, если проще по коду.
- B4 — только если у вас реально разные масштабы Windows на мониторах.

## 4. Смежное: отрыв вкладок

Отрыв уже переделан под браузерный жест (в 2.7.3–2.7.4): вкладка отрывается,
когда указатель выходит из полосы **в любую сторону** (или за окно), включая
уход в тело **своего** окна; драг тащит пиксап вкладки; бросок на свою полосу —
перестановка, на чужое окно — слияние, в пустоту/на тело своего окна — новое
окно, которое сразу показывает содержимое и получает фокус.

2. Какие у мониторов разрешения и **масштаб Windows** (100/125/150 %)?
3. В правке вы хотите, чтобы окно **раздувалось на весь экран** или
   **оставалось в прежних границах** (B2)?
4. Пропорцию редактор/превью вы предпочитаете настраивать один раз (доля) или
   она должна быть фиксированной константой?
